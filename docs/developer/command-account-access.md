# Command account access: independent-server handoff

Use this guide to connect the **company-operated Command server** to its own username/password gateway. These are integration instructions, not a statement that the company server or any employee account has been deployed. Do not point this gateway at the ChatGPT-hosted preview. The preview and an independently hosted installation have different identity boundaries. Changing a credential in one does not change a password in the other.

## Four different records

| Record | Source of truth | Rule |
|---|---|---|
| Employee, employment status, reporting line, authority and permissions | Application roster; stable person ID | Link all systems by this ID. A display name, job title, email or username is not the joining key. |
| Command login | Standalone credential database keyed to that roster ID | New hires choose a unique, non-email username in HR or Admin. The UI suggests one from their name, which can be changed before creation. Employee records with no issued work mailbox can be fully provisioned. On first credential issue, a legacy ID can serve as the username when valid; use the username returned by the gateway. Later issues preserve it. |
| Work Email | Optional issued mailbox on the roster (`companyEmail`) | Do not copy the old, generated hosted-login email into this field. Existing managers and actual department heads show only a recorded mailbox. For other existing employees the field initially appears blank; an authorized administrator can explicitly record a mailbox later. This changes contact details only. |
| Personal contact and legacy sign-in | Private HR contact record; separate legacy hosted binding | Do not copy private addresses into public cards, change hosted aliases in a mass migration, or use an applicant's address to grant access. Leave existing hosted sign-ins and stored personal contacts intact. |

## Set up the right servers, in this order

1. **Prepare an independent staging deployment first.** Back up the application database, file store, original encryption keys and roster configuration. Preserve stable person IDs and existing HR encryption material. Identify a previously authorized, active owner through the trusted roster and its owner verification policy (`verifiedOwnerRecord`). Do not manufacture owner status by inserting a new username, setting an email domain, editing seed names or promoting a random employee.
2. **Prepare the application upstream.** Use the repository's Worker entry point (`worker/index.ts`) or a port that implements the same trusted request boundary **before every route**; a static export or unsecured Next server does not implement this. Bind the real application `DB` and existing private storage/encryption facilities. Use the deployment's migration runner to apply any missing files under `drizzle/` in order, through `0023_relationship_portraits.sql` for this release (0022 adds the credential revocation outbox). Fresh DB: apply from the beginning. Existing DB: resume from its migration ledger. Never rerun historical inserts blindly or use a blank database as a replacement. Migration 0021 depends on the existing finance audit table, creates delegated session storage/indexes, and protects existing delegated audit entries. The credential database is separate and is initialized by the Node gateway.
3. **Make the network boundary explicit.** Employee browser → company's public HTTPS hostname → TLS proxy → gateway **public** listener → private application upstream. The application calls the gateway's **internal** listener to issue links; before redemption, the gateway calls back to the private application at `POST /api/internal/command/check-reset`. Both directions must work. Publish neither internal listener nor raw application endpoint. A public tunnel, public Worker endpoint, or hostname already used by the managed Sites preview is not a private upstream. A loopback address works only when both processes share that host/network namespace.
4. **Configure the environment.** Use a secret manager and independently generated service secrets; never ship them to browser code. Set no production secrets in the repository.

   | Setting | Component | Meaning |
   |---|---|---|
   | `COMMAND_AUTH_MODE=standalone` | Application/Worker | Requires the gateway trust boundary on this independent installation. Never set this as a switch to bypass the managed site's authentication. |
   | `COMMAND_PUBLIC_ORIGIN` | Gateway **and** app | Identical full public HTTPS origin, e.g. `https://command.example.org`, no path, query, credentials or fragment. The app also recognizes `COMMAND_AUTH_PUBLIC_ORIGIN`; avoid setting conflicting values. This is where employees open links. |
   | `COMMAND_UPSTREAM_ORIGIN` | Gateway | Private application origin, e.g. `https://command-app.internal`. Gateway accepts loopback, recognized private IPs or private hostname suffixes; remote private connections still require HTTPS. Plain HTTP is permitted only on loopback. |
   | `COMMAND_AUTH_INTERNAL_URL` | App | Private route to the gateway's **internal** control plane, e.g. `http://127.0.0.1:4101` when colocated, otherwise a protected internal HTTPS reverse proxy. Do not use the public employee login or the private app address here. |
   | `COMMAND_AUTH_INTERNAL_SECRET` | Both | Shared internal control-plane secret for the reset/eligibility exchange. Generate at least 32 random bytes encoded as hexadecimal. |
   | `COMMAND_AUTH_GATEWAY_SECRET` | Both | A **different** independently generated secret in the same format. Authenticates the gateway to the app; a client-supplied roster ID is never proof of identity. |
   | `COMMAND_AUTH_DB` | Gateway and offline operator | Absolute path to persistent private SQLite storage. Keep the service directory, database and WAL/SHM files restricted; use consistent encrypted backups and verify restores. |
   | `COMMAND_AUTH_PUBLIC_PORT`, `COMMAND_AUTH_INTERNAL_PORT` | Gateway | Loopback listener defaults: 4100 and 4101. Only proxy 4100 to the public hostname. Keep 4101 on the private control plane. |
   | `COMMAND_AUTH_TRUST_LOCAL_PROXY_IP` | Gateway, optional | Leave off unless the local reverse proxy overwrites the client-IP header from a trusted connection; it affects rate limiting. |

5. **Initialize and bootstrap.** Use a Node runtime with the project's required `node:sqlite` support (Node 22.13+). Create the private parent directory for the credential database. With the correct environment loaded, run `node standalone/command-auth/server.mjs` under a supervised service account. This initializes an **empty** credential store, not an owner. On a private console, verify the owner person ID against the actual application roster; then run the following with your verified IDs and an approved username. These strings illustrate arguments; they are not existing roster rows.

   ```sh
   node standalone/command-auth/operator.mjs bootstrap \
     --person=EXISTING_ROSTER_ID --verified-roster=EXISTING_ROSTER_ID \
     --username=AUTHORIZED_LOGIN --actor=VERIFIED_OPERATOR_ID \
     --reason='Authorized first account for this installation'
   ```

   Enter the new passphrase twice in the hidden prompts. Never put it on the command line, in a URL or in an environment variable. The CLI does not grant roles, create employees, or itself inspect the app roster: independent identity verification is the operator's responsibility. For protected-owner recovery, use the offline `rotate` command with the same arguments only after separate identity verification. The CLI refuses to bootstrap over an existing credential; rotation requires an active credential with the matching person and username. Ordinary employees use the Admin flow below.

## Staff setup and a real reset

1. In **Admin → People & Access → Add Site User**, choose **New Hire** (restricted onboarding) or **Existing Employee** (existing permissions, missing items queued). Set the unique Command username, employment details and supervisor. Enter Work Email only if one was actually issued. Creation does **not** send an invitation, provision an email mailbox, assign a password, or clear onboarding.
2. In the employee's card menu, select **Reset Password**, enter the reason (4–240 characters), and select **Create Reset Link**. The app authenticates the administrator, verifies authority for that individual, audits the request, and calls the private gateway. Only confirmed issuance yields a username, expiry and one-use link. **No email is sent.** An unconfigured or unavailable service returns a failure; do not display success or offer a pretend password.
3. Verify the recipient and hand them the link privately. The link expires after **30 minutes**; issuing another replaces the previous link. The employee sets and confirms their own passphrase (at least 15 characters, at most 512 bytes). The gateway revalidates issuer authority and target eligibility against the current app roster at redemption. A disabled user, revoked authority or failed callback must prevent redemption. Success invalidates existing sessions and reset links. The employee then signs in at `/auth/login`; resetting a password never releases an onboarding hold. A signed-in user who knows their password can change it at `/auth/password`.
4. Treat site access and credential status as distinct. Disabling the roster must deny access immediately. In standalone mode Admin/HR commits a durable revocation command for the private `/internal/command/deactivate` endpoint, which removes links, sessions and the password verifier. A failed external delivery remains pending for retry on admin demand or before reactivation; operation IDs and monotonic roster versions protect retries. On approved reactivation the roster stays blocked until revocation and the private `/internal/command/reactivate` handshake succeed. Then issue a fresh link; the old password does not return. Rehire through HR first if the employee is former. Test both sides before rollout, including an unavailable gateway and a safe retry; never infer success from a roster status badge alone.

## Who can do what

| Action | Authorization checks |
|---|---|
| Assist with a password | A verified owner may assist an eligible **other, non-owner** employee. A branch administrator must have owner-granted individual **Edit** on Users & Access and Reset Staff Passwords, be above the target's authority tier, manage the reporting branch and cover the target's module/HR permissions. No branch reset of another Admin-granted account. Active, onboarding and leave staff are eligible; disabled/former, self, and protected owners are not. |
| Open a delegated employee view | Verified owners, or individually owner-approved administrators with **Edit** on Users & Access and Delegated Access. Branch targets must be lower authority, in that reporting chain and without Admin permissions. Eligible target statuses are Active or Onboarding; self, disabled and owners are excluded. Templates cannot convey either sensitive grant. |
| Return to personal workspace | Employee view has a persistent banner. **Return to My Account** closes the preview, clears the delegated cookie and reloads the real administrator's workspace. It is not a logout or a password change. |

For a help request, go to **Admin → Delegated Access**, select the employee, enter a specific reason and choose **Open Employee View**. The preview is read-only and expires after **15 minutes**. It uses limited projections, not a second credential or unrestricted impersonation; private records, write paths, secrets and unapproved screens are blocked. Opening another tab cannot bypass the read-only boundary. Identity and authority changes are checked during use. The separate password-reset permission never follows automatically from the ability to inspect a workspace.

## Operational checks before enabling staff

- On the independent public origin, an unauthenticated browser gets the Command sign-in page; forged identity headers, public access to internal routes, or direct unauthenticated upstream traffic cannot grant access. Keep both service secrets server-side and do not forward the browser's login, recovery or CSRF cookies to the app. The gateway must pass the exact read-only delegation cookie `__Host-command-view` and stale-context signal `x-command-read-only` in their intended direction.
- Stage with synthetic accounts: issue a link to an employee with **no work email**, redeem once, reject reuse and expiry, verify the onboarding gate, exercise a lost-permission/disabled-target case, prove a new link invalidates an old one and test deactivation plus reactivation. Verify prior hosted accounts are unaffected.
- Open a delegated session to an eligible employee, verify writes and protected sections fail even by direct URL, then click **Return to My Account**. Confirm normal authority returns, the old token cannot be replayed, and real actor, subject, reason, start/end, expiry or revocation are recorded. Verify a view-only administrator cannot reset passwords.
- Preserve business audit records, not credentials. Do not log reset URLs/query strings, cookies, request bodies containing passwords, authorization headers, hashes of passwords, raw tokens or service keys in application, proxy, CDN, analytics, traces, ticketing or error logs. The app records reset requests and results; the gateway separately records credential events; the delegated-session audit is attributed to the real actor.
- Execute integration checks from repository root in staging: `node --test standalone/command-auth/gateway.test.mjs tests/admin/password-reset.test.mjs tests/security/independent-host-identity.test.mjs tests/security/delegation-boundary.test.mjs tests/security/delegation-integration.test.mjs tests/hr/work-contact.test.mjs`. Verify deployed topology manually: passing source tests cannot establish that private routes, secrets, DB backups or the intended production hostname were configured.
