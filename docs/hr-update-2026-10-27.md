# People & HR update — October 27, 2026

> Historical version 44 notes. The later same-day simplification update is documented in `hr-workflow-simplification-2026-10-27.md`; it supersedes the offboarding prerequisites described here.

## Scope and reason

This release is restricted to People & HR, its employee profile/photo entry points, protected HR APIs, and shared personnel projections needed by those screens. The user explicitly narrowed the work to HR. Account Management, Compliance/Claims, Work Orders, Vehicle Disposition, Finance screens and their business workflows are unchanged. The payroll comparison feature is removed from HR: comparison with ADP is an external owner activity, not a permanent product feature.

The initiating problem was that Payment Setup appeared to complete without exposing a usable bank setup workflow. The user required an audit of other controls that imply an operation happened when the program only stores a flag. A valid manual attestation remains appropriate for something done offline (for example, physical orientation or equipment return), but it must describe what occurred, who confirmed it, when, and the evidence/reference. It must not masquerade as an automatic payment, notification, carrier enrollment, or access revocation.

## Employee-first navigation and dashboard

The main HR areas use a persistent compact navigation rail with the selected-item triangle. Narrow screens use a single horizontal rail. Employee profiles group Personal & Work, Payment Details, Documents, Performance, Onboarding, Schedule & Attendance, and authorized Offboarding. People can move between employees through a searchable picker rather than repeatedly searching dropdowns. Directory filters remain behind a Filters control; columns are individual view preferences. Former employees and the organization chart remain available. No existing HR responsibility is removed by relocating it.

The overview shows real scoped workforce counts, optional self-reported gender composition, department staffing, hire trends, leave hours, approved nonexempt overtime hours, and recorded departures. Charts use stored records, not sample company statistics. Gender is optional and never inferred from a name or photograph; missing values remain Not Provided. No-data states are distinct from a measured zero. Employees without broad personnel visibility receive their own task/document/payment overview. Leave detail follows existing Timeclock access. Non-personnel catalog/payment delegates do not gain demographic access.

The later visual revision uses a compact analytical summary, workforce-composition panels and a visible HR work queue, with chart-to-employee drilldowns instead of decorative graphics. Hire-month cohorts exclude future and invalid start dates. Leave charts explicitly describe their start-month attribution; they do not pretend to allocate multimonth requests by actual daily use. Employee profiles reduce redundant navigation width while retaining an explicit route back to Employees.

The generic subtitle was removed. Screen actions state the task they perform. No empty HR panel is dressed up with fabricated completion or company data.

## Direct Deposit Setup

Accessible directly from the employee profile and the onboarding Payment Setup task. This is a dedicated workflow, not a generic record editor or a Verified checkbox.

The form collects account-holder name, Checking/Savings, ACH routing number, account number, account-number confirmation, financial institution, and requested effective date. Routing numbers receive ABA structure/checksum validation. The bankrouting.io lookup sends only the routing number; it does not send employee identity, account numbers, or other personnel data. The UI identifies the institution if the provider returns it. If the provider is unavailable or cannot confirm the bank, the employee may enter a bank name and the payroll reviewer must document manual verification. A routing lookup is not account ownership verification.

The employee can save a draft or provide an electronic authorization bound to the exact submitted account details and effective date. Server-side identity, time, authorization text/version and an account binding are recorded. Changing those instructions invalidates old consent. A payroll delegate may enter details for another person but cannot forge their electronic authorization; that path requires the actual uploaded and verified signed paper authorization, or subsequent employee authorization.

Submitted instructions require the assigned payroll review permission. Approved instructions are preserved; later changes create replacement instructions with effective dates. Masked summaries show only account last four; full bank details are retrieved through the protected dedicated endpoint and audited. Race guards prevent responses for one employee populating another employee's form. Generic HR record writes cannot bypass bank validation or authorization.

Protected values and files use the existing AES-GCM HR storage. The runtime HR_DATA_ENCRYPTION_KEY must remain unchanged unless performing an explicit key migration. This release does not connect an ACH processor, send deposits, perform microdeposit ownership verification, or enroll bank instructions in an external payroll service.

## Headshots

Employees may upload, crop/zoom, replace, or remove their own photo, including during onboarding. Scoped personnel/onboarding delegates can manage the appropriate employee's photo. Directory, profile, organizational views, and the existing user menu display the same protected photo. JPEG, PNG and WebP are validated for type/dimensions; metadata is removed; SVG is rejected. Stored bytes are encrypted, reads are authenticated, replacements use version checks, and writes are audited. No public object URL exposes personnel headshots.

## Job Description PDF

The original Job_Description_Template(3).docx is the layout reference. The generator now reproduces its Letter page size, two logos, matching embedded fonts, underlined Roman numeral headings, indentation, section order, page break before Section VI, footer and employee acceptance/signature block. Variable content wraps and paginates. Long duties do not overwrite the signature area or clip. Offer and corrective-action generators were not substituted with this template.

## Completion audit and resulting behavior

| Area | Previous risk | Current behavior |
| --- | --- | --- |
| Direct Deposit | Generic status could imply banking was configured | Dedicated account entry, saved draft, employee authorization and payroll review |
| Onboarding task editor | Client could propose Verified without supporting records | Generic writes preserve existing server verification and reject forged completion |
| Orientation | Single completion status | Trainer, actual date, covered topics, employee acknowledgment and attestation; signed-record path verifies the uploaded evidence |
| Pay and benefits approval | Verification could outlive changes to terms | Approval snapshots actual pay terms and benefit record/version; changes invalidate start readiness |
| Check payment | Payment status without usable delivery instructions | Approved delivery method and actual mailing address when mailed |
| Signed offer/job description | Check status could diverge from file | Readiness derives from the actual signed assigned document/version and current terms |
| Offboarding | Checkboxes implied Finance notification, account removal and final review | Closure checks actual Former/end-date/Disabled state and resolved time/corrections; requires dated named handoffs and documented equipment, physical access and benefit outcomes |
| Completed offboarding | Earlier checkbox-only histories looked authoritative | Legacy completion is marked Review Needed; newly completed reviews are immutable and follow-ups use a new record |
| Benefit enrollment | Dropdown could appear to enroll someone | Recorded election/assignment is labeled separately; enrolled status requires actual carrier/plan confirmation reference and date |
| Directory completion button | Button did not perform onboarding | Opens the actual onboarding checklist |

Offboarding does not automatically fire anyone, revoke access, contact Finance, return physical equipment, or issue final payroll. Those actions require their authorized systems or documented offline work. The completed HR review is a dated audit snapshot after the prerequisites have been verified. No change in this release grants managers new Admin permissions.

General HR tasks remain human task tracking. Completing a training follow-up does not automatically renew a license, clear a background check, or complete a government form. Carrier enrollment, payroll deduction posting and benefit/PTO accrual ledger posting are explicitly separate from the saved HR benefit assignment. These integrations remain work to implement and must not be advertised as automatic.

## Permission and history protections

Existing Admin responsibility checkboxes and employee scopes remain authoritative. Tax/banking reviewers receive the narrow payment portion of onboarding, without confidential offer/pay approval snapshots. Readiness is computed from full server records before those projections. The offboarding user interface receives only the actual account-status field necessary to show the access prerequisite, not the employee's permission grants. Employees cannot view management-only notes or offboarding decisions. Published corrective actions continue to require the verified signed current notice, and internal evidence is not automatically published.

No existing personnel data was bulk rewritten or marked complete by this update. No real employee bank account or disciplinary record was created for testing. Site access settings are unchanged.

## Verification and limits

Automated tests cover bank authorization, scoped access, completion forgery, current pay/benefit evidence, offboarding prerequisites, dashboard projections, photos, PDF layout, and the affected time/pay identity rules. The selected regression run passed 99 tests. TypeScript and whitespace validation passed; the official Sites build remains the publication gate.

The managed full-app local preview lacked its D1 tables and gateway user identity. We did not weaken authentication to work around it. Browser visual checks used the actual HR components in an isolated synthetic-data fixture, with saving disabled; that fixture is not included in the deployed source. Desktop overview, directory, profile, direct-deposit form, onboarding actions, orientation dialog and narrow-screen layout were inspected. A real mobile overflow defect was found and corrected. This is component visual QA, not proof that every live authenticated workflow has been exercised in the browser.

The job-description reference, populated two-page sample and long-content sample were rendered and inspected separately. Images were decoded after metadata stripping. Live institution-lookup access could not be independently confirmed from the execution environment (HTTP 403); bounded failure and manual-review paths are tested. External ACH execution, native government-form signing, carrier automation, historic personnel-file migration and authenticated acceptance tests with representative delegated users remain distinct deployment/rollout work.
